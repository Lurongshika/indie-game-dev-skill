# 项目架构

适用：工程初始化、模块拆分、数据组织、实现与重构。先检查现有工程；目录树本身不能证明依赖合理。

## 玩家体验与输入规范

- 明确界面层次和入口：主界面提供开始或继续游戏、设置和适用的退出入口；玩法界面承载游戏世界与必要 HUD；设置界面集中管理音量、显示、按键绑定等项目实际支持的选项。按游戏需求增设暂停、结算、存档选择等界面，不为不适用的平台或玩法强加功能。
- 定义主界面→玩法、玩法→暂停/设置、返回与结束等状态转换及返回目标；从暂停打开设置时，关闭设置应回到暂停界面并保持游戏暂停。区分全屏界面、HUD 和叠加弹窗的层级、焦点与输入归属，避免界面重叠遮挡、操作穿透或退出后残留。
- 设置的显示值应与实际生效值一致；明确应用、取消、保存和恢复默认的行为。进入玩法、暂停、恢复、返回主界面或退出时，按项目设计处理进度、音频及资源生命周期，并避免意外丢失进度。
- 尊重已有视觉风格与画面层级。不要擅自在游戏画面中大量增加说明文字、常驻提示或调试信息；新增文字必须有明确玩家需求，简短且不遮挡关键画面。剧情、无障碍信息和用户明确要求的文本按实际设计保留。
- 通过安全的实践机会、关卡布局、视觉或声音反馈逐步引导玩家理解目标、操作和后果；结合游戏类型决定引导强度，必要时提供简短、可关闭或可重看的提示。避免假定玩家已经知道玩法，也不要强制反复展示已完成的引导。
- 操作按键应在“设置 → 按键绑定”中集中显示，列出当前动作及其对应按键；支持多种输入设备时显示相应绑定。按项目范围实现可修改、冲突提示、恢复默认和保存设置，不声称未实现的功能已经支持。若已有不同菜单结构，沿用其设计并保证绑定易于找到。
- 游戏中的必要操作提示读取当前绑定并随设备或重映射更新，不把默认键位硬编码进素材或文本；首次引导与设置中的映射保持一致。暂停、菜单、弹窗和游玩状态明确输入归属，避免误触和操作穿透。
- 重要交互应有清晰反馈与可辨识状态；不要仅靠颜色、声音或短暂动画传递关键结果。菜单和交互应支持返回或取消，破坏性操作按需确认或允许恢复；保持反应、镜头、动画与玩法规则一致。
- 设计时考虑目标设备和实际能力：文字与图标可辨、焦点可见、控制方式可用；暂停、音量、字幕、动效或辅助选项按项目需求提供，避免凭空承诺所有无障碍功能。设置变更及存档行为要符合玩家预期，并处理失败。
- 以首次游玩者不受口头提示完成核心任务为引导验收场景，记录卡住的位置；验证主界面进入玩法、暂停进入设置并逐层返回、结算或返回主界面，以及按键显示、重映射后的提示、设置保存和暂停恢复。无法实际运行时明确标记待验证。

## 边界与数据归属

识别入口、运行状态、世界/关卡、实体、UI、内容、持久化和平台边界。每个边界回答：谁创建/释放？谁修改数据？调用者需要什么？失败如何反馈？

可选依赖方向：

```text
输入/UI → 用例或玩法规则 → 运行时状态
                         ↓
                    存档/平台接口
状态变化 → 显示与声音反馈
内容定义 → 规则读取
```

规则避免依赖具体按钮、动画节点或商店 SDK；适配层处理引擎/平台细节。小原型可以合并文件，但保留明确数据归属。

## 按修改关系组织文件

可选结构：

```text
game/
  bootstrap/       # 启动和运行状态
  features/        # player、combat 等，代码与专属资源相邻
  ui/              # 共享主题、组件、菜单
  content/         # 共享配置、关卡和文本
  infrastructure/  # 存档、平台适配
  tests/           # 关键规则和集成验证，按需创建
docs/              # 决策与制作规格
source_art/        # 位置依导入和仓库策略确定
```

不要为尚不存在的功能创建空框架。沿用引擎目录、元数据和导入规则，通过编辑器移动有引用的资源。确认忽略规则与可重建缓存；大二进制资产按需使用大文件方案，并确认协作者能取得文件。

## 通信与状态的选择

- 一对一且稳定：直接引用/接口通常足够。
- 多对象响应已发生的变化：事件/信号；明确发布者、订阅/退订与生命周期，避免隐式全局控制流。
- 互斥状态与合法转换：显式状态机，如菜单→游玩→暂停→结算，避免暂停时继续世界操作。
- 大量同类实体或实测性能压力：再评估 ECS、对象池或数据布局，不以“以后扩展”为由预搭全部框架。

可复用场景显式接收外部依赖，避免硬编码其他场景的内部路径。Godot 的 scene/signal/Resource、Unity 的 Prefab/Component/ScriptableObject、Unreal 的 Actor/Component/Data Asset 仅作概念映射；生命周期与序列化必须查对应版本官方文档。

## 内容、存档和验证

区分内容定义、运行状态、存档快照；使用稳定 ID 引用，不直接保存运行时对象引用。需要存档时定义 schema 版本、恢复入口、默认值、损坏处理、写入失败和旧版本兼容策略。按平台支持的方式安全写入，并验证中断不覆盖唯一可用存档，不假定跨平台替换具有相同保证。

文本使用可提取资源；配置说明单位、范围和缺省值。让内容工具报告重复 ID、缺失引用和非法范围，减少靠记忆维护一致性。

先打通启动→核心互动→反馈→退出/重进，需要时增加保存/恢复，再扩内容与抽象。交付职责表、依赖方向、数据唯一写入者、必要接口、迁移顺序和回归场景。用真实改动检验设计，例如新增敌人是否要修改无关 UI。性能结论依据目标设备 profiler；关键规则/存档兼容适合测试，低影响改稿无需空洞测试。

依据：[Godot Scene organization](https://docs.godotengine.org/en/stable/tutorials/best_practices/scene_organization.html)、[Project organization](https://docs.godotengine.org/en/stable/tutorials/best_practices/project_organization.html)。通用分层、存档约定和目录为综合建议，不是跨引擎强制标准。
