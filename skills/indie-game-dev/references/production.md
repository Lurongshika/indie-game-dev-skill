# 制作、范围与进度

适用：立项、工作分解、里程碑、产能不足与延期。

## 项目简报与范围

记录一句话体验、玩家、游玩场景、核心循环（行动→反馈→新选择）、体验支柱、平台/输入、团队容量与限制。把“类似某游戏”拆成机制、节奏或视觉特征，不照搬其完整规模。

建立必须、可选、明确不做三类清单。必须项删除后应确实导致核心体验不成立或无法交付。把范围改为可计数预算：关卡、敌人、独特动画、道具、对话节点、文本量、语言、平台；在没有产能数据时保持为估算。

## 阶段及退出条件

| 阶段 | 要回答的问题 | 可观察的退出条件 |
|---|---|---|
| 核心原型 | 关键互动是否产生目标体验 | 最少资产下可操作；观察玩家，决定继续/调整/停止 |
| 代表性切片 | 体验和生产流程能否一起成立 | 一段代表性游玩含必要 UI、画面、文本/声音，可导出构建并测出单位内容成本 |
| 内容制作 | 能否稳定复制质量 | 按内容清单集成，依据实际吞吐更新预测 |
| 全流程版本 | 是否能从启动到设计终点 | 无阻断路径，主要系统/内容已集成，可保留未完成表现 |
| 候选发布 | 是否满足交付条件 | 核心回归通过，已知问题和接受理由明确，构建可复现 |

阶段名称不是行业统一定义，验收条件才是约定。原型不必有宣传画质；切片无需囊括所有系统。内容驱动或生成世界项目按风险调整验证顺序。

## 工时与排期

任务按可验收结果拆分，如“暂停后修改音量并在重启后保留”，而不是“做设置”。记录 ID、结果、负责人、依赖、乐观/常规/悲观工时、估算依据、完成条件和状态。

容量 = 每人真实可投入工时 − 已知会议/维护/其他占用。并行受技能和依赖限制，不能只把总工时相加。优先最高风险、最难替代和最长依赖链的工作。

显式计入集成、返工、反馈、打包与不确定性。无历史数据时给区间和假设，不套固定缓冲比例。切片后用“同类内容实际工时 × 剩余数量 + 一次性工作 + 风险余量”重估，考虑学习与复杂度变化。

短期细化、远期保留里程碑粒度。进度报告给可玩构建、已验收体验、阻塞、范围变化和预计影响，避免用“完成 80%”替代证据。

## 跨模块分解示例

“上锁的门”的顺序：规则（钥匙、失败原因、打开状态）→架构（交互、物品条件、持久化）→UI/文本（动作、原因、当前映射键）→美术/声音（锁定与打开反馈）→验收（有/无钥匙、重复交互、读档、输入切换）。按项目删去不需要的系统。

延期先区分需求增加、估算偏差、返工、技能瓶颈和外部依赖。删减低核心价值且高成本的数量/变体，评估资产替代与表现简化；调整期限时展示范围/产能依据。保留可交付版本，不靠持续加班填平计划。新想法放后续版本，必要变更注明影响。

依据：[Derek Yu — Finishing a Game](https://makegames.tumblr.com/post/1136623767/finishing-a-game) 的原型、核心、范围和完成经验；[Harry Florencio — Pre-Production](https://www.gamedeveloper.com/game-platforms/what-you-should-take-out-of-pre-production) 的切片、管线与验收。容量公式和阶段表为本 skill 的综合模板。
